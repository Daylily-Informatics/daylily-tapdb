# TapDB 11 requirement matrix

Source: Dayhoff `20260929_tapdb_integrity_external_reference_requirements.md`. User amendments: no EUID issuance redesign; independent immutable storage deferred to #117. Preservation clauses remain applicable without a new global uniqueness guarantee.

| Requirement | Ledger | Disposition | Original requirement |
|---|---|---|---|
| ID-01 | P02 | IMPLEMENTED — typed selectors/results and identifier contract; UID-overlap qualification | Define the scope and meaning of every exposed identifier: local row UID, globally issued EUID, external opaque UUID/barcode, tenant UUID, authenticated subject, request/idempotency key, and revision token. Public interfaces must identify which is accepted and returned. A syntactically valid identifier is not proof of persistence or ownership. |
| ID-02 | P01 | SUPERSEDED — administrator owns namespace assignment | Guarantee that different objects in the supported federation cannot receive the same global EUID text through valid independent deployments. Include templates, instances, lineage, audit identities, external-reference objects, and any other allocator-backed EUID family. Service-qualified routing is necessary but does not by itself satisfy this bare-EUID requirement. |
| ID-03 | P01 | SUPERSEDED — administrator owns namespace assignment | Specify and enforce disjoint issuance authority. Invalid overlapping namespace/range/issuer assignments must fail provisioning/startup or issuance explicitly. Support independent object work after authorized provisioning; do not introduce a mandatory per-object call to another service merely to allocate identities. |
| ID-04 | P02 | PRESERVED — adoption hashes and allocator-floor receipts; no fleet collision audit or issuing redesign | Preserve existing issued identities. A new format or allocation strategy must not silently rename objects, rewrite references, move sequences backwards, or assert old collisions never existed. Produce read-only collision/overlap diagnostics before any later authorized cutover. Ambiguous old identities fail explicitly; any repair is separately approved. |
| ID-05 | P02 | PRESERVED — native recovery fences/floors and explicit principal admission; no new clone authority | Cloning/restoring a database must not create a second independent active allocator with overlapping authority. Preserve non-reuse after rollback/restore, include published or externally observed identities in recovery-floor reasoning, and fail closed when authoritative issuance/recovery evidence is missing. |
| ID-06 | P02 | PRESERVED — typed external coordinates; retained identities across isolated restores | Preserve real object identity across replicated/restored copies of the same object while distinguishing new issuance. Local UID reuse in another database is not a global collision and must not be treated as identity equivalence. External UUIDs must retain namespace/issuer/type context even if statistically unique. |
| AUD-01 | P03 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Constrained application runtime roles have no effective ability to UPDATE, DELETE, TRUNCATE, or soft-hide audit history. Cover direct grants, inherited roles, PUBLIC/default privileges, ownership, writable columns/views/routines, and relevant DDL/trigger-disable authority. Preserve appropriately scoped reads. |
| AUD-02 | P03 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Runtime callers cannot fabricate authoritative audit entries by direct INSERT. Preserve legitimate trigger-generated capture through a narrowly controlled native path. If an initial release retains direct INSERT temporarily, classify the integrity requirement as only partially met. |
| AUD-03 | P03 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Domain writes and their required audit entries commit atomically. If audit capture fails, the domain mutation fails. Capture every supported write route, including native APIs, GUI-backed calls, bulk operations, upserts, lineage reactivation, and SQL executed with a supported constrained writer role. Inventory any exceptions explicitly. |
| AUD-04 | P03 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Existing audit entries are immutable; corrections append attributed new evidence referencing what was corrected. Protect audit storage with defense-in-depth mutation rejection as well as privileges. A soft-delete flag on an audit entry is not an acceptable way to hide history. |
| AUD-05 | P03 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Templates, instances, lineages, canonical external references and authoritative history cannot be physically deleted through ordinary runtime operations, including truncate/cascade paths. Preserve supported soft-delete semantics and explicit, guarded restoration. Distinguish operational ephemeral data from authoritative records; classification cannot be a loophole for deleting domain history. |
| AUD-06 | P05 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Each change retains sufficient typed old/new content, object and relationship identities, server time, and transaction/revision context to support HIST. Full initial state must be retained at creation, including canonical template/version identity. Lineage history includes endpoints, relationship type, scope, properties, and deletion/reactivation state. |
| AUD-07 | P03 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Enforce the same contract in fresh provisioning, principal binding/rebinding, supported migration, restore, and drift validation. Existing-role reconciliation must be explicit and reviewed; changing future default grants alone does not fix deployed roles. |
| AUD-08 | P13 | DEFERRED — issue #117 filed | Separate runtime tamper resistance from privileged-administrator assurance. Document exactly what owners/superusers can bypass. Define an independently protected evidence export/integrity-verification contract for stronger assurance; do not claim that a hash chain in the same mutable database is sufficient. |
| ATTR-01 | P04 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Define a native transaction attribution envelope distinguishing initiating actor type and stable subject/issuer, authenticated executing service/principal, tenant/scope, request correlation, and operation identity. Record database-generated timestamps and revision/transaction context; do not rely on a client clock as authoritative. |
| ATTR-02 | P04 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Human-initiated writes retain both the human identity and the executing system. Unattended automation uses an explicit service actor; do not invent a human or label all unknown activity as the application. Subject identifiers are opaque validated strings, not necessarily UUIDs. Preserve identity-provider issuer and subject together. Email is display context unless the provider's defined subject contract says otherwise. |
| ATTR-03 | P04 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Make context transaction-scoped, mandatory for supported writes, and safe with pooled connections. Missing or malformed required attribution fails explicitly. Neither context leakage to the next request nor silent conversion of an unrepresentable subject to null is acceptable. |
| ATTR-04 | P04 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Distinguish asserted actor context from cryptographically/authentically verified provenance. An application-set PostgreSQL session variable alone does not prove a human identity. Specify the trust boundary: how the authorized application supplies the subject, how TapDB binds the executing principal/scope, and what a compromised authorized service could still falsify. |
| ATTR-05 | P04 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Expose paginated, authorized history queries by object/lineage EUID, actor, executing service, request/operation, time interval, and revision. Preserve cross-service correlation when callers provide it; never infer identity equivalence merely because emails or request strings match. |
| ATTR-06 | P04 | CONTRACT COMPLETE — documented consumer writer inventory/adoption; owning-service rollout remains separate | Provide a consumer adoption contract and inventory. TapDB cannot recover a human identity never supplied by Atlas or Bloom. Publish missing-envelope diagnostics and an explicit transition plan; do not claim that installing a package fixes consumer propagation automatically. |
| HIST-01 | P06 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Expose read-only reconstruction of retained object and lineage state at an explicit revision or consistent historical boundary. Include soft-deleted records and the template contract governing their interpretation. Define ordering under concurrent transactions; timestamps alone and sequence allocation order alone must not be assumed to equal commit order. |
| HIST-02 | P06 | IMPLEMENTED — bounded local cycles, missing/truncated results, governing template identity; semantic interpretation remains with owner | Support reconstruction of a bounded selected subgraph with its relevant historical relationships and endpoints. Report missing history, external boundaries, incompatible schema/template interpretations, and truncation explicitly. Do not return a partly reconstructed graph as complete. |
| HIST-03 | P06 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Provide a read-only correction proposal/diff against a selected historical state, including expected current revisions, affected nodes/lineages, soft-delete/reactivation effects, dependencies, and attribution. No mutation occurs merely by previewing history or a proposal. |
| HIST-04 | P06 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Applying an approved correction creates new attributable revisions; it never erases intervening history, reuses old operation identities, rewinds allocators, or restores an entire database to correct a few objects. Preserve unrelated newer work and reject changed preconditions atomically. |
| HIST-05 | P06 | IMPLEMENTED — missing owner validator refuses apply; consumer validators remain owner work | Run structural constraints and application-owned validation through supported interfaces before correction. Native local persistence can be atomic; clinical semantics remain with the owner. No direct SQL bypass of application rules is implied. |
| HIST-06 | P06 | BOUNDARY DOCUMENTED — local retained assertions only; no remote/physical reversal | Local history may preserve external reference assertions and last verified evidence, but it does not reconstruct or roll back Bloom's owned state or physical laboratory actions. Cross-service corrections require owner operations and explicit outcomes; do not promise a distributed rollback transaction. |
| HIST-07 | P06 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Existing incomplete history must remain honestly incomplete. If an adoption baseline is needed, retain an explicitly dated baseline capture as new evidence without changing old audit rows or claiming it represents unrecorded past states. Automatic historical repair/backfill is outside scope. |
| XRF-01 | P07/P08 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Preserve typed opaque identifiers separately from service-owned TapDB object targets. Opaque targets carry namespace, kind, value, and explicit tenant/global scope. UUID/barcode values must not be relabeled as EUIDs. Reference EUIDs are real locally persisted identities. |
| XRF-02 | P07/P08 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Provide or qualify a public, supported create-or-resolve operation for an independent canonical external reference without requiring a fabricated unrelated source object or live owner request. Registration is explicit and idempotent. The planner must inspect existing current interfaces before proposing an addition; the baseline's private _claim_reference is not a supported client API. |
| XRF-03 | P07/P08 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Canonical external references may participate in permitted typed generic lineages as graph objects, including participation in an Atlas session and order/kit associations, without introducing a second local authoritative tube entity. Define endpoint validation, issuer ownership, tenant isolation, and who may assert each relationship. |
| XRF-04 | P07/P08 | SUBSTRATE IMPLEMENTED — typed reference association preserves original identity; owner verification is consumer work | Preserve the original opaque reference EUID and target facts when later associating it with a verified service-object reference. Use an explicit typed assertion/lineage between identities of the same external object. Never mutate opaque target coordinates into Bloom coordinates or replace upstream relationships just because the owner becomes reachable. |
| XRF-05 | P07/P08 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Support canonical-target immutability and clear handling of optional enrichment. Conflicting non-null identity facts fail explicitly. Separate supplied assertions from owner-verified evidence; merely registering a reference does not prove the remote object exists. |
| XRF-06 | P07/P08 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Give applications a supported place for names, display facts, participation/modification annotations, and verification evidence without adding arbitrary keys to canonical target properties or using private writer tokens. Prefer existing sanctioned annotation/lineage mechanisms. If a linked annotation record is necessary, it is metadata about the reference, not a second physical-object identity. |
| XRF-07 | P07/P08 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Registration, binding assertion, and detachment/reactivation preserve attribution and history and support expected revisions/idempotency. Concurrent duplicate claims return the same canonical identity or a precise conflict. Generic primitive support must let Atlas enforce its one-active-Bloom-binding rules without a race; TapDB must not impose a universal one-to-one rule on all external reference uses. |
| XRF-08 | P07/P08 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Registration and local lookup/traversal work without remote network calls, broker connectivity, an event consumer, or owner admission. Tenant/scope authorization remains required locally; offline capability is not permission to claim another tenant's object. Owner verification is an explicit separate action. |
| XRF-09 | P07/P08 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Native query/projection APIs expose reference identity, typed assertions, and verification provenance consistently, with a local-only traversal option and explicit incomplete results. They must not silently fetch remote objects, register references, or persist query snapshots during reads. |
| CORE-01 | P09 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Ordinary native object/reference/lineage CRUD and history reads require no broker, outbox dispatch, message delivery, workflow engine, or decision result. Mandatory atomic audit remains on. If any current helper couples these operations, identify and separate that dependency without disabling audit. |
| CORE-02 | P09 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Qualify shared optimistic-revision and short-transaction locking primitives for objects, existing edges, and competing new-edge creation. Provide a supported conflict result and atomic expected-revision checks wherever missing. Do not move Atlas's 120-second edit leases, inactivity policy, or one-cell-per-session UI rule into TapDB. |
| CORE-03 | P09 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Generic persistence invariants and audit controls apply to every supported writer, not only one ORM page. Clearly identify direct owner/superuser SQL as outside runtime guarantees. Do not claim an Atlas lock governs direct Bloom writes. |
| CORE-04 | P09 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Tenant admission and runtime scope changes remain explicit, reviewed native operations. Creating an organization object or an XRF must not silently expand database privileges. Expose sufficient read-only diagnostics for owning services to detect missing tenant admission and mismatched reference scope. |
| CORE-05 | P09 | PRESERVED — consumer validators/cardinality; cycles permitted; no clinical rules moved into TapDB | Keep business rules such as patient roles, one active tube association, containment semantics, and assay revisions in consuming applications unless already declared generic constraints. Do not enforce that every lineage graph is acyclic; restrict cycle rules to relationships whose declared semantics require it. |
| OPS-01 | P10/P12 | COMPLETE — exact 10.1.11 baseline, 47-row matrix, source manifest and focused evidence | Reconcile these findings against an exact current revision. Map each requirement to existing support, a proposed change, a consumer dependency, or an unresolved question. Existing qualifying capability should be documented and tested later, not rewritten automatically. |
| OPS-02 | P10/P12 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Plan fresh installation and explicitly approved existing-installation adoption separately. Inventory schema, grants, templates, allocator authorities, and history capabilities read-only before proposing migration. No broad reseeding, silent template overwrite, identity rewrite, or historical data cleanup. |
| OPS-03 | P10/P12 | SOURCE CONTRACT COMPLETE — versioned envelope/templates/interfaces; publication pending G3 | Publish versioned contracts for any changed templates, attribution envelopes, schemas, or native APIs, with clear consumer adoption steps. Do not overwrite immutable template versions or install compatibility shims/inferred defaults without an explicit proposal. |
| OPS-04 | P10/P12 | IMPLEMENTED / FOCUSED QUALIFIED — see evidence map below; not production acceptance | Backups/restores must preserve objects, lineage history, attribution, external references, audit integrity controls, allocator non-reuse, and reviewed principal scopes. Provide inspectable verification receipts and report excluded external artifacts. Reuse existing native recovery/fence tooling and extend only demonstrated gaps. |
| OPS-05 | P10/P12 | IMPLEMENTED — native catalog/grant/epoch/completeness diagnostics; no deployed RPO/RTO claim | Provide diagnostics for effective grants, trigger/routine protection, configured issuance authority, history completeness boundaries, and relevant version provenance. Diagnostics cannot claim an operating backup schedule, RPO/RTO, or owner-service recovery succeeded without deployment evidence. |
| OPS-06 | P10/P12 | PENDING G3 — release notes prepared; no package/tag published or consumer deployed | Release notes must state exact guarantees and residual limits, required consumer changes, applicable PostgreSQL versions, and any breaking changes. Plan one final immutable annotated numeric tag/build after the implementation is ready, rather than repeated exploratory service rebuilds. Consumers and deployment changes require separately approved scopes. Container builds must run on the designated EC2 builder, never the laptop. |

## Source and qualification evidence

The 47 original requirements above retain their wording. Their dispositions are
bounded by the approved plan amendments. “Implemented / focused qualified” means
local source plus the selected isolated checks, not exhaustive proof of every
possible writer or consumer deployment. All 38 checks passed on PostgreSQL 16.13.

| Requirement group | Native source | Focused evidence |
|---|---|---|
| ID-01,04–06 | `audit.py`, existing identity inventory/recovery, `integrity_lifecycle.py` | Overlapping numeric UIDs; exact-source adoption hashes; current and 10.1.11 restores. Existing issuer/allocator logic preserved. |
| AUD-01–07 | `schema/rls.sql`, `audit_storage.py`, runtime principal/catalog contracts | Direct audit INSERT/UPDATE/DELETE/TRUNCATE, inherited/column privileges, role assumption, routine misuse, disabled trigger drift, audit failure atomicity, domain truncate rejection. |
| ATTR-01–05 | `security_context.py`, connection/runtime adapters, `audit.py` | Non-UUID human subject, service context, missing/malformed context, pool reset, actor filters, host identity checks, API attribution. |
| HIST-01–07 | `history.py`, `revisions.py`, `owner_validation.py`, epoch/baseline schema | MVCC concurrent commits/savepoints/rollback; soft deletion/reactivation; bounded cycles; stale object and endpoint correction; owner validation and durable retry. |
| XRF-01–09 | `external_references.py`, annotation template and DB guards | Independent concurrent claims; annotation authority/CAS; reconcile and stale edge; competing binding validator; tenant/global rejection; local-only history/reference reads. |
